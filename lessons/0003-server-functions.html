Server functions

~13 min · The createServerFn RPC pipeline, and when to pick it over an API route. Cheat sheet: Server functions reference.

← 0002: File-based routing Cheat sheet →

Lesson 0001's auth guard (getAuthState) was the simplest possible server function. This repo has dozens of richer ones in src/server/fn/ — with validators, with middleware. This lesson takes the mechanism apart: the validator → middleware → handler pipeline, and — the thing you asked to nail down — when you reach for it instead of an API route.

The modelAn RPC, not a fetch

React Router had no answer for “run this on the server from my component” — you'd write a separate endpoint and fetch it. A server function collapses that into a single typed function: 

// Define (server): runs ONLY on the server.
export const getAuthState = createServerFn({ method: 'GET' }).handler(
  async () => ({ user: await getVerifiedUser() }),
)

// Call (client or server): looks local, crosses the network.
const { user } = await getAuthState()   // ↔ a GET happens under the hood

The handler body is server-only (Lesson 1's execution model: it's stripped from the client bundle). When the client calls getAuthState(), the router fires a network request to the server, which runs the handler and returns the result. That round-trip is the RPC. No URL to design, no JSON to parse by hand, full types end to end.

The pipelineFour stages, in order

Here's a richer one from src/server/fn/jobs.ts:

export const fetchJobs = createServerFn({ method: 'GET' })
  .middleware([authMiddleware])
  .handler(async ({ context }) => {
    const { data, error } = await jobsQuery(context.supabase)
    if (error) throw new Error(`Failed: ${error.message}`)
    return data
  })
StageWhat it does
{ method }'GET' for cacheable reads; 'POST' (the default) for mutations.
.validator(fn)Parses + validates the caller's input. Its return value becomes the typed data the next stages see.
.middleware([...])Runs before the handler; can enrich context (attach a DB client, a session, etc.).
.handler(({ data, context }) => ...)The actual logic. Server-only. Returns a serialisable value.

Validator and middleware are optional. getAuthState takes no input and needs no preprocessing, so it skips both. fetchJobs needs no input either but wants the user-scoped DB client, so it adds middleware (no validator). Add stages as the function needs them.

Where data and context come from

  • data is the validator's output — the caller's input, parsed and typed. No validator → no data. (See signIn below for a validator in action.)
  • context is assembled by middleware. Each middleware's .server() return is merged in — so authMiddleware hands fetchJobs the context.supabase it reads above.
The real middleware, from this repo 
// src/server/middleware/auth.ts
export const authMiddleware = createMiddleware({ type: 'function' }).server(
  async ({ next }) => {
    const { client, session } = await requireUserClient()
    return next({ context: { supabase: client, session } })
  },
)

Now any function with .middleware([authMiddleware]) gets context.supabase (a user-scoped client) and context.session. Company scoping is enforced by Row-Level Security on that client — not by a manual .eq('company_id', …) filter. (Middleware can also have a .client() side — see the cheat sheet.)

Validators in action 
// src/server/fn/auth.ts
export const signIn = createServerFn({ method: 'POST' })
  .validator(z.object({ email: z.string().email(), password: z.string().min(1) }))
  .handler(async ({ data }) => {
    // data is typed: { email: string; password: string }
    …
  })

The validator is both a guard (rejects bad input) and the source of the handler's typed data.

The payoffServer function vs API route

This is the distinction you asked to lock in. They're the two ways to put code on the server in Start. Both run server-side; the difference is the interface they expose:

Server function (createServerFn)API route (server.handlers)
InterfaceA function callA real URL + HTTP method
TypesEnd-to-end (input + output)Manual — you parse the Request
Pick it forApp code calling the server; no public URL neededWebhooks, cron, third-party fetches

The decision is simple: does something external need a URL to hit?

  • Yes (Dodo posting a payment webhook, a cron scheduler, a third-party fetch) → API route.
  • No — it's just your app calling the server → server function.
This repo uses exactly that split
  • Server functions → all data access: fetchJobs, createJob, getAuthState, the auth fns. Typed calls from your components/loaders.
  • API routes → only external triggers: api/webhooks/dodo (Dodo payments), api/webhooks/email, api/webhooks/cal-booking, and api/cron/*. Real URLs that outside services POST to.

Same question every time: does an outsider need a URL? Jobs data → no → server fn. Dodo webhook → yes → API route.

PracticeRead a server function

Try it in your repoWhy that middleware?

Open src/server/fn/jobs.ts (fetchJobs) and src/server/middleware/auth.ts (authMiddleware). Then answer, using the decision rule above:

  • Why is fetchJobs a server function and not an API route? (It's called from your components/loaders to read data — no external service needs a URL → server function.)
  • Why does it use authMiddleware instead of resolving the Supabase client in the handler? (So every protected function shares the same user-scoped client + session setup, and RLS owns company scoping. The handler stays focused on the query.)
  • Why does fetchJobs have no validator? (It takes no input — the user identity is resolved in middleware, not passed by the caller. Compare signIn, which does validate input.)

That first point is the refactoring instinct worth having: when you see the same server pre-logic (auth, DB client, tenancy) repeated across handlers, that's a signal to extract a middleware — exactly what authMiddleware does here.
