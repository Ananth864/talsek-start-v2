Lesson 0001 · TanStack Start

The execution model: what runs where

~10 min · The foundation every other lesson stands on. Save the cheat sheet: Execution Model reference.

← First lesson Cheat sheet →

You want to read TanStack Start code and know, at a glance, whether a line runs on the server or in the browser — well enough to catch it when AI gets that wrong. That single skill rests on one mental model. This lesson builds it.

The one ideaStart is Router + a server

TanStack Start is not a brand-new thing. It is TanStack Router — the type-safe router you can almost feel through your React Router instincts — with a server layer bolted on. The docs are blunt about it: Start “relies 100% on TanStack Router for its routing system,” and adds SSR, server functions, API routes, and middleware on top (Overview).

So when you're orienting in any Start file, ask two questions, in order:

  1. Routing question — which route is this, and how does it fit the tree? (You already have the instincts for this from React Router.)
  2. Execution question — does this code run on the server, in the browser, or both? (This is the new muscle.)

This lesson is the second question. Get it right and the rest of the framework unlocks.

The defaultEverything is isomorphic

Here is the rule that surprises everyone, and the one most AI-generated code gets subtly wrong:

Core principle

All code in TanStack Start is isomorphic by default — it is included in and runs in both the server bundle and the client bundle, unless you explicitly constrain it. (Execution Model guide)

That includes a plain helper:

// runs on BOTH server and client
function formatPrice(price: number) {
  return new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(price)
}

And — this is the gotcha — it includes route loaders:

export const Route = createFileRoute('/products')({
  loader: async () => {
    // ISOMORPHIC: server during the initial SSR request,
    //             client during later in-app navigation.
    const r = await fetch('/api/products')
    return r.json()
  },
})

If you assume “loader = server,” you'll approve code that quietly ships database logic to the browser. Don't assume it.

The boundaryTwo environments

Your code lives in one of two worlds. The boundary is what each can reach:

ServerClient (browser)
Node / edge runtimeBrowser runtime
File system, databases, process.env, secretsDOM, localStorage, user events
During SSR, on server-function calls, at buildAfter hydration, during client-side navigation

Control APIsPinning code to one side

When “both” isn't safe (a secret, a database, a browser API), you pin code to one side with one of these. Learn the shape of each — recognising them in AI output is most of the job:

APIRuns onIf called on the other side
createServerFn() Server Client call becomes a network request (an RPC)
createServerOnlyFn(fn) Server Throws
createClientOnlyFn(fn) Client Throws
createIsomorphicFn() Both — a different body each —

The headline one is createServerFn. Calling it from a component doesn't run the function locally — it fires a network request to the server, which runs the .handler() and returns the result. That round-trip is the type-safe RPC. Everything you'd normally build a separate API route + fetch for, Start gives you as a function call. 

// Runs ONLY on the server. The client call below is a network request.
const fetchUser = createServerFn().handler(async () => await db.users.find())

// In a component:
const user = await fetchUser() // a fetch happens under the hood

From React RouterWhat's actually new for you

You already know routing. Here's the delta Start adds over plain React Router:

  • SSR by default. The first render of a page happens on the server, then the browser hydrates and takes over. React Router was client-only; Start is not.
  • Code runs in two places now. In React Router, everything was the browser. In Start, you must reason about the boundary — this lesson.
  • Server functions replace hand-rolled APIs. Where you'd fetch('/api/x') in React Router, in Start you call a server function directly and it type-checks end to end.
  • Loaders are isomorphic. React Router's loaders were client-side. Start's run on the server and client. (See the gotcha above.)

PracticeClassify where it runs

Five snippets. For each, decide: does it run on the Server, in the Client, or Both? Immediate feedback follows each answer. The last one is the red flag worth memorising.

Red flagsWhat to catch in AI output

Three smells that mean “stop and fix” when you're reviewing AI-written Start code:

Secret at module scope

const KEY = process.env.SECRET at the top of a file. Leaks to the client bundle and is undefined on edge runtimes. Move it into a createServerOnlyFn or a handler.

DB / env inside a loader

A loader touching a database connection or process.env directly. Loaders are isomorphic — that runs in the browser too. Have the loader call a createServerFn.

Hydration mismatch

Rendering new Date(), Math.random(), or DOM-dependent values straight into markup. Server and browser disagree → React warns and re-renders. Gate with useHydrated() or compute in useEffect.

Try it in your repoThe auth guard

Open src/routes/_member.tsx (the pathless layout for signed-in pages) and src/server/fn/auth.ts. The guard is a server function called from beforeLoad: 

// src/server/fn/auth.ts
export const getAuthState = createServerFn({ method: 'GET' }).handler(
  async () => ({ user: await getVerifiedUser() }),
)

// src/routes/_member.tsx
beforeLoad: async ({ context, location }) => {
  const { user } = await context.queryClient.ensureQueryData({
    queryKey: ['member-auth-state'], queryFn: () => getAuthState(),
  })
  if (!user) throw redirect({ to: '/signin', search: { redirect: location.pathname } })
  /* ...return profile context for the child routes */
}

Read it with your new model and answer, for yourself:

  • The getAuthState handler — server, client, or both? (It's a createServerFn: server only. The getVerifiedUser() identity check never reaches the browser.)
  • beforeLoad calls getAuthState(). On the first page load (SSR), where does that call resolve? On a later in-app navigation? (Server both times — but via different mechanisms: SSR on first load, an RPC round-trip on later nav.)
  • Why is a route guard “UX, not security”? (The real data boundary is Supabase Row-Level Security on the user-scoped client — the guard just keeps unauthenticated users out of the UI surface.)

If you could answer those, you just used the model on real code — exactly the verification skill the mission is after.

Key termsSeeded glossary

Isomorphic
Code that runs in (and is bundled for) both server and client. The Start default.
SSR
Server-side rendering — the server produces the first HTML; the browser hydrates it into an interactive app.
Hydration
The browser attaching React's event handlers to the server-rendered HTML, making it interactive.
RPC
Remote procedure call — calling a server function from the client looks like a local function call, but crosses the network. createServerFn is Start's RPC.
Server function
A function created with createServerFn — runs on the server, callable from the client. Start's replacement for hand-rolled API endpoints.

These seed a glossary that will grow each lesson; for now they also live in the execution-model reference.
