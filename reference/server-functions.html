Server functions

The createServerFn RPC pipeline. Companion to Lesson 0003. Primary sources: Execution Model, Middleware, Auth primitives.

A server function runs only on the server but is called from the client like a local function. The call becomes a network request (an RPC). It is Start's replacement for hand-rolled fetch('/api/...').

The pipelinemethod → validator → middleware → handler

// from src/server/fn/jobs.ts
export const fetchJobs = createServerFn({ method: 'GET' })
  .middleware([authMiddleware])
  .handler(async ({ context }) => {
    const { data, error } = await jobsQuery(context.supabase)  // client came from middleware
    if (error) throw new Error(`Failed: ${error.message}`)
    return data
  })
StageRoleRequired?
{ method }'GET' for cacheable reads, 'POST' (default) for mutationsOptional (defaults POST)
.validator(fn)Parse + validate the caller's input; its return becomes typed data downstreamOptional
.middleware([...])Run before the handler; enrich context (e.g. attach supabase, session)Optional
.handler(({ data, context }) => ...)The actual server logic. Server-only.Yes

The simplest form skips validator + middleware — like getAuthState = createServerFn({ method: 'GET' }).handler(async () => ({ user: await getVerifiedUser() })) in src/server/fn/auth.ts.

MiddlewareThe real pattern from this repo

// src/server/middleware/auth.ts
export const authMiddleware = createMiddleware({ type: 'function' }).server(
  async ({ next }) => {
    const { client, session } = await requireUserClient()
    return next({ context: { supabase: client, session } })
  },
)

Now any function with .middleware([authMiddleware]) gets context.supabase (a user-scoped client) and context.session in its handler — that's how fetchJobs reads context.supabase above. Company scoping is enforced by Row-Level Security on that client, not by a manual filter. Middleware can also have a .client() side (runs in the browser before the call).

ValidatorsInput parsing (zod)

// src/server/fn/auth.ts
export const signIn = createServerFn({ method: 'POST' })
  .validator(z.object({ email: z.string().email(), password: z.string().min(1) }))
  .handler(async ({ data }) => {
    // data is typed: { email: string; password: string }
    return client.auth.signInWithPassword(data)
  })

The validator is both a guard (rejects bad input) and the source of the handler's typed data. No validator → no data.

The contrastServer function vs API route

Two ways to put code on the server. Both run server-side; the difference is the interface:

Server function (createServerFn)API route (server.handlers)
InterfaceA function callA real URL + HTTP method
TypesEnd-to-end (input/output typed)Manual (parse the Request yourself)
Use whenApp code calling the server; no public URL neededWebhooks, cron, third-party fetches
In this repoAll data access (fetchJobs, createJob, auth fns)Webhooks (api/webhooks/dodo & co.), cron (api/cron/*)

The decision rule: does something external need a URL to hit? Dodo payments posting a webhook, or a cron scheduler pinging an endpoint → API route. Your components calling the server → server function.

// src/routes/api/webhooks/dodo.ts -> an API route, because Dodo POSTs to a URL
export const Route = createFileRoute('/api/webhooks/dodo')({
  server: { handlers: { POST: async ({ request }) => { /* verify + process */ } } },
})

Red flagsWhat to catch in AI output

Mutation with no validator

A POST server function that takes input but has no .validator() — the handler's data is untyped/untrusted. Always validate mutation input (this repo does, with zod).

Using GET for a mutation

A write (create/update/delete) on { method: 'GET' }. GETs are cacheable and may be replayed/prefetched. Use POST (the default) for mutations — see createJob vs fetchJobs.

Secret at module scope outside the handler

Reading process.env.SECRET at the top of the file still leaks (Lesson 1). Inside the .handler() or .server() it's safe — that's the server-only boundary. Watch where the read sits.

Returning non-serialisable values

A server function returns across the network — it must be serialisable (JSON). Returning a Supabase client, a class instance, or a function breaks the call. Return plain data.
