The Execution Model

Where TanStack Start code runs. Companion to Lesson 0001. Primary source: Execution Model guide.

One sentence to remember: everything is isomorphic by default — it runs in both the server and client bundles unless you explicitly constrain it. The APIs below are how you constrain it.

Core principleIsomorphic by default

Code with no special marker runs on both server and client. That includes a surprising amount — plain helper functions, business logic, and route loaders (server during the initial SSR request, client during later navigations).

Why some take (fn) and others don't

The “Only” variants — createServerOnlyFn(fn), createClientOnlyFn(fn) — are simple wrappers: they pin one function to one side and crash on the other. Nothing to configure, so you hand them the function directly. createServerFn() and createIsomorphicFn() take no fn — they are builders you chain (.validator().middleware().handler() or .server().client()). Rule of thumb: “Only” = wrapper (takes fn); everything else = builder.

Don't confuseLoaders vs create*Fn

These are different categories, not alternatives. A common mistake is to treat them as rival ways to fetch data.

The idiomatic pattern composes them: the loader (lifecycle) calls a server function (safe server access). Putting DB or process.env code directly in a loader is the anti-pattern below — because the loader runs in the browser too.

File-levelImport protection

Mark a whole file so its imports can never leak across the boundary:

  • Filename suffix: *.server.ts / *.client.ts
  • Or a side-effect import at the top: import '@tanstack/react-start/server-only' (or client-only)

Both markers in one file is an error. See the Import Protection guide.

Red flagsWhat to catch in AI output

Secret read at module scope

const KEY = process.env.SECRET at the top of a module.

Why it leaks. process.env is a Node API, yes — but the line of code that reads it sits in an isomorphic module, so the module is shipped to the client bundle too. Two things can then happen to that line in the browser: the bundler statically replaces process.env.SECRET with the literal secret string (the leak — it's now plain text in your client JS), or it leaves the reference and the browser throws process is not defined. Both wrong. (On edge SSR runtimes there's a third problem: env is injected per-request, so a module-scope read runs before the env exists and is undefined even on the server.)

Why the fix works. Wrapping the read in createServerOnlyFn (or putting it inside a .handler() / middleware) marks that code server-only → import protection strips it from the client bundle entirely. The read now happens at call time, on the server — it never reaches the browser. ⚠️ Moving it inside a loader does not fix it: loaders are isomorphic, so the line still runs in the browser.

Assuming a loader is server-only

A route loader that touches process.env or a DB connection directly. Loaders are isomorphic — that code also runs in the browser. Fix: have the loader call a createServerFn.

Hydration mismatch

Rendering time/random/DOM-dependent values straight into markup. Server and client produce different HTML → React warns and re-renders. Fix: compute in useEffect or gate with useHydrated().
